# Four-player 100 BB candidate campaign — preparation, not launch

PR406 qualifies the existing native tools at small tables. Its20M cap freezes around37–39M nodes; it establishes neither mature throughput nor adequate coverage. The combined five/six feasibility task adds no more four-player cost pilots. PR404's running200BB campaign retains bb128 exclusively.

## Recommended next allocation

Build the first **four-player research candidate**, initially one fresh lineage with fixed **3B and10B** endpoints, current100BB/K50/v1-menu/unprunedfast16/eight-roots/full-average recipe and a declared **250M-key freeze threshold**. This is a bounded capacity choice to test, not a sufficient-capacity claim. Preserve within-lineage membership, earlier checkpoint and pre-freeze telemetry. Independent lineages and release acceptance follow separately; no seed selection, node extension or search.

Before proposing launch, specify one fresh seed, exact inputs/build/config, all output hashes and a complete model+binary+evaluation allocation. Use existing bb128 mature costs, including PR404 when complete, with explicit player-count uncertainty and load/save/audit reserves. M4's3–4-second traversal windows cannot price this campaign as measured bb128 performance. Do not promise8–12hours from traversal arithmetic alone. Training/save/export/audit, binary conversion/full-row parity, model startup, play, replay/reproduction, readout/report and storage are separate components. No further cost-pilot ladder is proposed.

250M keys may freeze much earlier than3B. Measure retained per-street coverage and missing/zero/positive-mass decisions without treating table-wide zero mass as fallback rate. Training after freeze can refine only retained keys. Keep capacity/adverse evidence even if development returns look promising.

## Required evaluation plumbing

The existing generic policy-play tool already supports four players; the current paired arena is three-player-specific. Qualify a four-player paired arena before substantive candidate evaluation. A policy sees only its legal observation. Own trace hidden cards belong exclusively to independent replay/evaluation. Require legal actions, pot/chip accounting, complete four-seat schedules, source/model pins and byte-identical reproduction. Reuse one read-only loaded table per distinct model, with separate policy/RNG state per seat.

Use fresh paired deals and **all24 seat permutations** per independent block; permutations do not create24 independent observations. Freeze counts/roots and report intervals over independent deal blocks. A development primary compares10B and3B as focal players against the **same fixed three3B opponents**, rather than changing the entire field between arms. Include four homogeneous fields (random, check-call, TAG, pot-pressure) and fixed mixed fields (two check-call+pressure; random+twoTAG;3B+check-call+pressure). All lineups and adverse results remain in the report. Development is not v0.7 acceptance and cannot replace independent-seed fresh confirmation.

Counts, multiplicity families, practical regression margins and power scenarios need a concrete proposal before hands. Three-player variances are historical scenarios only, not four-player pass chances. No automatic larger count when an interval is inconclusive. A later release protocol must set independent-seed and scenario requirements prospectively.
